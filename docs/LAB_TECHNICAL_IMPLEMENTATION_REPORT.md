# 小红书云手机采集系统：技术实现说明

**项目名称：** 5507 手机小红书采集项目

**文档用途：** 实验室技术说明与后续验收依据

**资料汇总截止：** 2026-09-15（基于项目源码、开发记录、校准证据与验证文档）

## 1. 项目目标与当前边界

本项目建设的是一个运行在 **真实 Android 云手机** 上的小红书图文笔记采集系统。它不以网页移动端、浏览器模拟或生成数据替代手机 App；关键词搜索、筛选、进入详情、字段读取、数据保存、暂停恢复和导出，均由本机上的普通程序控制已登录的小红书 Android App 完成。

系统的第一阶段采用单设备架构：一台云手机、一个控制主机和一个本地持久数据库。当前实现已提供桌面 App 和命令行两种——「入口，日常运行不依赖 Codex、云端大模型或大模型密钥。实验室仍负责登录、处理验证码或登录失效、检查异常页面，并对最终记录进行人工核验。

本报告需要特别区分以下四个层次：

| 层次 | 含义 | 当前情况 |
| --- | --- | --- |
| 工程实现 | 程序、数据库、桌面界面、恢复和导出能力已经写入并测试 | 已完成 |
| 真实设备校准 | 指定云手机、当前小红书版本及真实 UI 页面可由规则读取 | 已完成基础校准 |
| 小批量实机验证 | 真实 App 中的搜索、详情、可靠身份、暂停与恢复等行为 | 已完成部分验证 |
| 最终成果验收 | 3 个关键词各 10 篇、共 30 篇不同笔记，均经人工核验 | 仍需按验收规程完成 |

因此，系统已经具备真实采集和独立运行能力，但不能将软件测试、历史记录重算或单关键词采集直接表述为“30 篇最终验收已经完成”。

## 2. 整体技术架构

系统采用“原生桌面界面 + Python 控制层 + Android 自动化 + PostgreSQL 持久化”的分层设计：

```text
小红书采集助手.app（SwiftUI / AppKit）
        │ JSONL 请求、响应与进度事件
        ▼
Python 控制层与任务执行器
        ├── 任务状态机、限速、暂停、恢复、预算与冷却
        ├── 页面规则、字段解析、身份核验与质量判断
        ├── 本机设备互斥锁
        └── 数据库事务、证据保存与导出
        │
        ▼
ADB + uiautomator2 设备适配器（始终指定 serial）
        │
        ▼
真实 Android 云手机 → 小红书 App
        │
        ├── UI 树 XML
        ├── 页面截图 PNG
        └── 当前设备/App/页面元数据
        │
        ▼
PostgreSQL 17 持久数据库 + 本地证据目录 + CSV/JSONL 导出
```

设计重点是把“点击手机”和“可审计的数据采集”分开处理：Android 自动化模块只负责与特定设备交互；解析层只从经校准的真实页面读取字段；存储层负责将记录、进度、运行状态和证据引用持久化。这样既便于定位问题，也为后续增加 Worker 或多设备调度保留了清晰接口。

## 3. 开发路径与关键实现

### 3.1 设备接入与真实页面校准

当前校准设备为 Android 12 / API 31、720 × 1280 分辨率的云手机，当前小红书版本为 **9.46.0**，包名为 `com.xingin.xhs`。本机通过回环地址转发访问设备，程序要求每一条 ADB 操作都显式指定设备 serial，避免多设备环境中误操作“第一个已连接设备”。

`doctor` 诊断入口依次检查 ADB、设备状态、Android 信息、前台应用、自动化服务、截图、UI 树和中文输入能力。它的作用是把“手机无法连接”“自动化服务不可用”“小红书版本未适配”和“当前页面无法读取”拆开报告，而不是把所有异常都写成连接失败。

页面规则不由代码猜测。开发过程先从真实设备采集首页、搜索输入页、结果列表、图文详情、正文展开前后等截图和 UI 树，再将唯一性、父子结构、可见边界和页面上下文写入本地校准配置。没有相应真实样本和唯一匹配依据的控件，不进入生产规则。这样可避免 App 更新后由于误点、误读或控件 ID 变化产生静默错误。

### 3.2 采集流程

一次关键词任务按以下有限流程执行：

1. 检查设备、自动化服务、App 版本和本地数据库是否可用。
2. 打开小红书搜索页，输入并回读中文关键词；依据已校准的结果页规则筛选图文笔记。
3. 逐篇进入详情页，读取标题、作者和正文等基础字段；只在所需字段未读到、或补读已校准的时间/话题字段时进行有限滚动。
4. 保存详情截图、UI 树、页面元数据和字段级证据引用；随后回到结果列表继续扫描。
5. 在任务结束、部分完成、暂停或异常停止时，从数据库导出 CSV 与 JSONL。

采集器不下载图片或视频，也不采集评论正文。字段没有读取到时保留空值和原因，不以 `0`、猜测内容或模型生成文本补齐。

### 3.3 基础字段、正文和质量状态

当前的任务目标以“基础字段可读”计数：标题、作者和正文已读取即可计入；页面证据明确证明笔记没有展示标题时，保留这一特殊状态。它不等于笔记已经人工验收，也不等于身份已经去重。

此前系统把“正文是否在单屏显示完整”当作自动门槛，会导致长正文虽已读取但没有被计入。质量升级后，系统不再自动判定正文完整性，统一写入：

| 字段 | 当前规则 |
| --- | --- |
| `base_readable` / `eligible` | 标题、作者、正文的基础可读性，供任务目标计数使用 |
| `body_complete` | 固定为 `null`，不以页面高度或省略号自动推断 |
| `completeness_status` | `not_assessed`，表示等待人工核对 |
| 缺失字段原因 | 分别标明标题、作者或正文为何未读到 |
| 原文与证据 | 不改写保存的原文，始终保留截图、XML 和字段证据引用 |

历史 103 条已有观察记录已经在备份后重新评估：基础字段可读数量由旧规则下的 48 条变为 99 条；页面时间原文可读数量由 4 条变为 98 条。原始标题、正文、作者、证据、任务目标和已使用预算均已逐条核对保留；旧判断留存在审计表 `quality_assessment_audits`，没有删除历史数据。

### 3.4 时间和平台话题

时间字段只保存用户在页面上实际看到的原文，例如“昨天上午 11:10 广东”。系统不将相对时间推算为未经证实的年份、日期或时区；若原文以“编辑于”开头，则单独标为编辑时间，不能冒充首次发布时间。

程序已具备平台话题的字段、来源和证据接口，但当前真实 UI 树把蓝色话题文字与普通正文合并在同一个、没有子节点的文本控件中。由于无法独立确认它是平台话题，当前配置不会把正文里的普通 `#词组` 自动转成标签，而会明确显示“平台话题未能识别”。这是一项真实页面适配限制，不代表笔记没有话题；当后续版本提供可验证的话题组件、可访问性信息或安全的跳转行为时，才可加入正式规则。

### 3.5 可靠身份与重复控制

系统只用可靠的平台笔记 ID 作为自动去重键。获取流程是：在当前笔记详情页打开已校准的“分享”入口，执行“复制链接”，只读取这一次操作后 Android 手机上的新剪贴板内容；若复制的是短链接，程序只允许在受限的小红书链接域名内解析重定向，得到标准笔记链接后才提取 ID。Mac 剪贴板不参与，不会发送内容给联系人，也不读取链接网页的正文来替代 App 采集。

得到可靠 ID 后，系统立即查询同一任务中是否已有基础字段可读成果：

- 同一可靠 ID：跳过之后的详情字段采集，不重复推进目标。
- 不同可靠 ID：即使标题或正文相同，也分别保留，不能因为文本相似而合并。
- 无法取得 ID：保存该次独立观察并标为 `unverified`，基础字段可读仍可计入任务目标，但最终“不同笔记数”必须由人工核对。

任务恢复时重新执行同一搜索条件并从列表重新扫描。程序从已持久化的可靠 ID 中识别已采集内容，而不把旧坐标、卡片序号、滚动位置或文本指纹当作跨重启的可靠身份。

### 3.6 证据、数据库与导出

每条观察记录关联真实页面的截图、UI 树和哈希清单；元数据包括采集时间、设备标识、App 版本、前台页面和字段读取方式。时间、正文或其他字段若来自补充读取，则各自保留独立的证据引用，避免把不同笔记的页面片段错误拼接。

数据库使用 PostgreSQL 17，采用 SQLAlchemy 和 Alembic 管理模型与迁移。核心对象包括：

| 对象 | 用途 |
| --- | --- |
| `Task` | 一个关键词任务的目标、状态、预算、冷却、连续异常计数和停止原因 |
| `Run` | 一次执行/恢复的运行记录、开始结束时间和事件 |
| `Observation` | 一次真实详情页观察的原文、质量、身份、字段证据和来源 |
| `Batch` / `BatchItem` | 多关键词按顺序执行的批次及子任务归属 |
| `Review` | 人工接受/拒绝、审阅人和人工身份结论 |
| `QualityAssessmentAudit` | 质量规则迁移前后的历史判断审计 |

一条观察记录与任务进度在同一数据库事务中提交；如果数据库写入或证据保存失败，记录不能被算作成功。截图和数据库属于两个不同的存储系统，因此系统会保留证据失败状态并要求修复，而不会声称两者天然是跨介质原子提交。

CSV 与 JSONL 都从数据库生成。新导出格式为 schema version 2，保留 `eligible` 兼容字段，但其含义已明确为“基础字段可读”；CSV 为降低公式注入风险，会对部分展示字段加前导单引号，完整原值仍保留在 JSONL 与 `record_json` 中。

### 3.7 暂停、恢复、限速和异常处理

系统采用持久化状态机，而不是依赖运行进程内存。正常暂停、意外退出和控制管道关闭都会在安全边界停止新设备动作，并保留已提交的结果。关闭桌面窗口不会停止采集；主动退出 App（⌘Q）则请求安全暂停并等待采集进程结束。

异常处理遵循有限、可解释的原则：

| 情况 | 系统行为 |
| --- | --- |
| 瞬时读取失败 | 有限等待和重试；成功读取后清除连续读取失败计数 |
| 页面操作后无实际进展 | 独立记录连续无进展计数；页面真正前进后清除 |
| 连续 10 次读取失败或无进展 | 安全暂停，要求用户明确“检查并继续” |
| 频率限制 | 持久化冷却截止时间；重启不清零，不提供跳过冷却功能 |
| 登录失效、验证码、未知页面 | 保存证据并等待实验室正常处理，不尝试破解或绕过 |
| ADB 暂时断开 | 在设备锁内有限恢复；重新识别页面，必要时重新搜索 |
| 数据库/证据保存失败 | 停止新增采集，避免产生无法证明来源的成功计数 |

为保护页面操作，主动 UI 操作间隔保持至少 3 秒。详情访问、列表滚动、连接恢复等预算均在任务创建时持久化，暂停、恢复和重启不会自动重置。每词目标可以设置为 1–500；500 条时系统会保存最多 1,500 次详情访问和 750 次列表滚动预算，但这只是执行上限，不代表任何关键词一定能取得 500 篇人工确认的不同笔记。

### 3.8 导航性能优化

最初的实机瓶颈主要是远程云手机读取，而不是 3 秒操作间隔。一次完整页面读取曾包含 UI 树、补读、PNG 传输和元数据读取；其中大尺寸 PNG 传输占明显时间。优化后将两类读取拆开：

- 搜索、输入回读、筛选、列表定位和等待页面变化，只读取轻量页面状态（UI 树、前台状态和必要元数据），不传输 PNG。
- 进入详情保存记录、发生故障或需要保留证据时，才执行完整截图和 UI 树采集。

对同一静止页面的实测中，完整读取由 26.090 秒降至 17.431 秒，约减少 33%。在同一关键词的可比搜索检查点中，旧记录约为 147–148 秒，新版首轮约为 65.5 秒；完整搜索流程约为 72.5 秒。网络、页面内容和云手机负载会影响耗时，这些数据是实测样本，不是所有批次的速度承诺。

## 4. 桌面应用与独立运行

日常入口是 macOS 原生应用 **“小红书采集助手.app”**。界面使用 SwiftUI/AppKit，Python 采集控制层作为独立子进程运行；两者通过带请求编号的 JSONL 消息通信。技术日志不会混入界面事件，界面每 3 秒只读取数据库进度，不重连手机，也不与采集进程争夺设备。

App 将原有终端菜单重组为三页：

| 页面 | 功能 |
| --- | --- |
| 开始采集 | 单关键词/多关键词统一输入、重复关键词合并、每词 1–500 条、采集当前手机笔记 |
| 任务与结果 | 查看进度、暂停/继续、预览原文和证据、查看身份与质量状态、导出 CSV/JSONL |
| 设备连接 | 查看设备、自动化服务、App 适配和数据库状态；提供检查和打开云手机入口 |

打开 App 时只异步准备连接，不会自动启动或恢复采集任务。手机连接模块支持健康连接复用、有限重连和设备状态检查；实际状态以指定 serial 的 ADB `device` 状态和只读 shell 往返为准，不能把 TCP 端口可达当作手机已连接。连接、自动化读取、App 适配、任务读取失败和设备占用在界面上分别呈现，避免出现“页面读取异常却显示手机未连接”的误导。

## 5. 测试、校准与已验证结果

工程验证采用三层：

1. **Synthetic 单元/集成测试**：用明确标注为 synthetic 的 XML、页面和故障夹具覆盖解析、恢复、预算、去重、导出、设备锁和异常状态机。
2. **隔离 PostgreSQL 集成测试**：使用显式 `TEST_DATABASE_URL` 指向专用测试库，验证迁移、事务、一致性、恢复和幂等；测试库不与真实采集库混用。
3. **真实手机验证**：在当前云手机和小红书 9.46.0 上校准页面、中文搜索、图文筛选、详情、可靠链接、暂停恢复和证据保存。

质量升级工程记录中，Python 测试为 **899 项通过**，原生桌面界面 synthetic 自检为 **36 项通过**；这些测试证明实现逻辑和隔离数据库行为，不能计作真实笔记成果。另有 500 条的完整状态机 synthetic 测试，用于验证目标、预算与恢复，不替代真实 500 条采集。

真实设备校准已获得首页、搜索、图文详情、分享入口、复制链接、返回详情、长正文尾部和时间显示等证据。小批量验证已确认：可靠笔记 ID 获取、暂停后保留已提交成果、关闭窗口后后台继续运行、恢复搜索时按已知可靠 ID 跳过重复详情，以及一次读取失败后恢复保存。最终 3 个关键词 × 10 篇、跨关键词 30 篇不同笔记、逐篇人工核验和实机断连恢复，仍应按独立验收清单执行。

## 6. 后续扩展到 100 台设备的准备与限制

当前模块已从第一版区分 `device_id`、`session_ref`、`task_id` 和 `run_id`，任务执行器通过设备接口操作手机、通过存储接口提交结果。这使增加 Worker、设备管理器和调度器有明确切入点。

但第一阶段的设备互斥是单控制主机、同一状态目录下的本机 `flock`，不能当作 100 台或多主机的分布式锁。扩展前必须新增并验证以下能力：

- 原子任务领取、设备归属和任务/设备租约续期。
- 失去租约的旧 Worker 不能继续控制手机或提交过期状态的 fencing 机制。
- 跨 Worker、设备和会话的共享限速、冷却、暂停、心跳和故障隔离。
- 跨 Worker 的可靠身份幂等、集中可观测性、网络分区和多机故障恢复测试。
- 按 5、10、25、50、100 台逐级进行真实部署验证，而不是直接以接口存在宣称已有 100 台吞吐能力。

因此，本阶段的成果是为多设备系统建立可复用采集核心和数据契约，而不是已经完成分布式 100 台集群。

## 7. 实验室建议的后续验收流程

1. 在云手机中正常登录并确认当前小红书版本与已校准版本一致；若 UI 变化，先运行诊断与页面快照，不直接开始批量任务。
2. 从桌面 App 或普通终端创建 3 个真实关键词任务，每词初始目标 10 条。
3. 对每一条候选记录核对截图、UI 树、标题、作者、完整正文和身份；无可靠 ID 的记录由审阅人建立跨任务一致的人工身份键。
4. 在至少一个真实任务中验证暂停/继续，并在正常方式下进行一次设备断开与恢复检查。
5. 运行验收报告，确认每个关键词各有 10 篇、总计 30 篇不同且人工接受的笔记；随后从数据库重新导出 CSV/JSONL 并复核一致性。
6. 将关键词、任务 ID、审阅人、入选记录、证据位置、异常记录、导出文件和未解决适配问题一起归档。账号密码、AccessKey、ADB 凭据及原始敏感连接信息不进入公开报告。

## 8. 结论

项目已经实现了从真实 Android 云手机上的小红书搜索，到详情字段读取、证据留存、数据库持久化、暂停恢复、可靠 ID 去重和 CSV/JSONL 导出的完整单设备工程闭环。系统的核心特点是以真实页面证据、明确质量状态和持久化恢复为基础，而不是只执行脆弱的点击脚本。

当前最重要的后续工作是完成规定的 3 × 10 人工验收，并持续维护小红书版本与页面规则的真实校准。自动平台话题识别仍受当前 UI 树结构限制；该功能已保留接口，但不会在缺少可验证证据时把正文 `#词组` 误写为平台标签。
